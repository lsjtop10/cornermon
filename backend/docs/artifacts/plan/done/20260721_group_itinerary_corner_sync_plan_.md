# 코너 추가/삭제 시 조 순회표(Itinerary) 동기화 (compact)

## 요구사항
`Group.itinerary`가 배지 등록 시점에 1회 스냅샷된 뒤 코너가 추가/삭제돼도 갱신되지 않아, 캠프
진행 중 코너를 추가/삭제하면 이미 등록된 조들의 순회표가 실제 코너 목록과 어긋나던 문제 수정.

## 왜 이렇게 했는가
- 컬렉션 diff(추가/삭제 원소 추적) 없이 메모리에서 슬라이스를 고치고 `Save`로 전체 덮어씀 —
  `Group.itinerary`가 자체 ID 없는 Value Object 컬렉션이고 JSONB 컬럼 하나로 통째로 직렬화되므로.
- 코너 동기화 트랜잭션과 기존 방문 시작/종료 트랜잭션이 같은 Group 행을 동시에 건드리면
  lost update가 나므로, 낙관적 락 대신 **비관적 락(`SELECT ... FOR UPDATE`)** 채택 — 캠프 규모(조
  20개, 관리자 최대 2명)를 고려하면 낙관적 락의 재시도 복잡도보다 단순한 비관적 락이 적합하다고 판단.
  UC-1/2만 잠그고 방문 시작/완료 4개 지점을 안 잠그면 락이 무의미하므로 반드시 함께 처리.
- 범위 제외(사용자 확인): 배지 등록 시점의 코너 목록 스냅샷 자체(별도 잠금 필요, 동시 발생 거의
  없다고 가정), 코너 삭제 시 `ON DELETE CASCADE`로 방문 기록이 사라지는 문제(soft delete가 맞는
  방향이나 범위가 달라 별도 이슈로 분리 — 하드블록으로 바꾸는 대안은 완료된 방문이 있으면 코너를
  영구히 못 지우게 돼 기각).
- PR #160(조회 시점 필터링)과는 대체 관계가 아님 — 원본 itinerary까지는 필터링 안 되므로, 코너가
  `IN_PROGRESS` 방문을 가진 채 삭제되면 유령 항목이 남아 해당 조가 이후 어떤 코너에서도 방문을
  시작 못 하는(`ErrGroupBusy`) 소프트락 버그가 있었음 — 이번 변경(쓰기 시점 정리)이 이를 막음.
